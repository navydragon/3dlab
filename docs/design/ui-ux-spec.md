# UI/UX Specification

## Интерактивная цифровая лаборатория машин и механизированных процессов транспортного строительства

**Статус:** Draft  
**Версия:** 0.1

**Связанные документы:**
- `docs/vision/strategic-vision.md`
- `docs/product/mvp-scope.md`
- `docs/product/learning-goals.md`
- `docs/product/user-flows.md`
- `docs/domain/domain-model.md`
- `docs/domain/simulation-model.md`

---

## 1. Назначение документа

Этот документ фиксирует UX/UI-принципы первого MVP и описывает:

- основные пользовательские контексты;
- информационную архитектуру интерфейса;
- состав экранов;
- поведение 3D-сцены;
- способы перехода между машиной и процессом;
- представление расчётов и экспериментов;
- требования к обратной связи;
- минимальные адаптивные и доступностные требования.

Документ определяет поведение продукта, но не задаёт конкретный frontend framework или библиотеку компонентов.

---

## 2. Главный UX-принцип

Интерфейс должен поддерживать три уровня работы:

```text
Изучить объект
→ Понять его роль в процессе
→ Принять решение на уровне системы
```

При этом пользователь может начать:

```text
с машины
```

или:

```text
с процесса
```

и перейти к одному и тому же производственному контексту.

---

## 3. Основная навигационная модель

Главная страница MVP должна предлагать три смысловых входа:

```text
[ Машины ]
[ Процессы ]
[ Производственная задача ]
```

### Машины

Ведёт к изучению отдельных технических объектов.

### Процессы

Ведёт к изучению технологических процессов и этапов.

### Производственная задача

Ведёт к практическому сценарию:

```text
экскаватор + автосамосвалы
```

с расчётом производительности и затрат.

Третий вход может появиться уже после первого vertical slice, но архитектура интерфейса должна его предусматривать.

---

## 4. Глобальный layout

Основной учебный экран рекомендуется строить по схеме:

```text
┌──────────────────────────────────────────────────────────────┐
│ Header / Breadcrumbs / Context                               │
├───────────────┬──────────────────────────────────────────────┤
│               │                                              │
│ Learning      │              Main workspace                  │
│ / Context     │              3D / process / simulation       │
│ panel         │                                              │
│               │                                              │
├───────────────┴──────────────────────────────────────────────┤
│ Timeline / parameters / experiment controls / status         │
└──────────────────────────────────────────────────────────────┘
```

На небольших экранах панели могут складываться вертикально.

---

## 5. Header

Header должен содержать минимум:

- название продукта или компактный логотип;
- breadcrumbs;
- текущий контекст;
- действие возврата;
- при необходимости кнопку возврата на главную.

Пример:

```text
Главная / Процессы / Земляные работы / Разработка грунта
```

При переходе в машину из процесса:

```text
Главная / Процессы / ... / Разработка грунта / Экскаватор
```

Кнопка:

```text
← Назад к этапу «Разработка грунта»
```

должна быть предпочтительнее абстрактного:

```text
← Назад
```

когда контекст известен.

---

## 6. Главная страница

Главная страница не должна быть перегружена.

Минимальные блоки:

### 6.1. Заголовок

```text
Интерактивная цифровая лаборатория
машин и механизированных процессов транспортного строительства
```

### 6.2. Краткая идея

```text
Изучайте машины, переходите к технологическим процессам
и исследуйте, как технические решения влияют на производительность,
сроки и стоимость работ.
```

### 6.3. Три входа

Карточки:

```text
Машины
Процессы
Производственная задача
```

### 6.4. MVP-область

На первом этапе пользователь должен видеть, что доступен учебный модуль:

```text
Земляные работы:
экскаватор + автосамосвалы
```

---

## 7. Каталог машин

MVP-каталог содержит:

```text
Гидравлический экскаватор
Автосамосвал
```

Карточка машины должна содержать:

- название;
- короткое назначение;
- изображение/thumbnail;
- статус глубины контента;
- основные связанные процессы.

Пример:

```text
Гидравлический экскаватор

Разработка грунта и погрузка в транспорт.

Связанный процесс:
Разработка и транспортирование грунта

[Открыть]
```

---

## 8. Учебный модуль машины

Для экскаватора основной layout должен включать:

```text
Обзор
Конструкция
Как работает
Рабочий цикл
Параметры
Производительность
Где применяется
```

Это могут быть:

- вкладки;
- боковая навигация;
- последовательные секции.

Важно, чтобы пользователь всегда видел, где он находится внутри модуля.

---

## 9. Экран «Обзор»

Содержит:

- крупное название;
- 3D-preview или hero-view;
- краткое назначение;
- типовые операции;
- ключевые параметры;
- связанные процессы.

Цель:

> За 20–30 секунд дать студенту целостное понимание объекта.

---

## 10. Экран «Конструкция»

Главная зона — интерактивная 3D-модель.

Боковая панель содержит:

```text
Основные узлы
- Ходовая часть
- Поворотная платформа
- Силовая установка
- Стрела
- Рукоять
- Ковш
- Гидроцилиндры
```

При выборе узла:

- объект подсвечивается в 3D;
- камера при необходимости мягко фокусируется;
- справа/слева появляется карточка узла;
- отображается назначение;
- при наличии показываются связанные параметры и операции.

---

## 11. Поведение выбора в 3D

Выбор должен работать в обе стороны:

### Из списка

```text
нажал «Ковш»
→ ковш подсветился в 3D
```

### Из 3D

```text
нажал на ковш в модели
→ выбралась карточка «Ковш»
```

Выбранное состояние должно быть одинаковым независимо от способа выбора.

---

## 12. Визуальные состояния 3D-объектов

Минимально:

```text
default
hover
selected
dimmed
hidden
```

Желательно:

```text
isolated
transparent
```

Для selected должен быть один очевидный визуальный акцент.

Не следует одновременно использовать несколько конкурирующих эффектов.

---

## 13. 3D controls

Обязательно:

- orbit;
- zoom;
- reset camera;
- fit object.

Желательно:

- preset views;
- isolate component;
- transparency;
- exploded view.

Пользователь не должен случайно «потерять» объект за пределами камеры.

Должна быть кнопка:

```text
Сбросить вид
```

---

## 14. Экран «Как работает»

Цель — объяснить принцип работы без глубокого погружения в механику гидросистемы.

Содержит:

- 3D-модель;
- упрощённое объяснение рабочих движений;
- последовательное включение стрелы, рукояти и ковша;
- контекстные callouts.

Пользователь должен понимать:

```text
движение стрелы
движение рукояти
движение ковша
поворот платформы
```

---

## 15. Экран «Рабочий цикл»

Главная зона:

- 3D-анимация рабочего цикла;
- timeline;
- текущая фаза;
- controls.

Фазы:

```text
1. Разработка грунта
2. Заполнение ковша
3. Подъём
4. Поворот
5. Разгрузка
6. Обратный поворот
```

Controls:

```text
Play
Pause
Restart
Previous phase
Next phase
Speed
```

---

## 16. Timeline рабочего цикла

Timeline должен быть не декоративным.

Он должен показывать:

- порядок фаз;
- активную фазу;
- переходы между фазами;
- при наличии — расчётное время.

Нажатие на фазу:

```text
→ перемещает демонстрацию к этой фазе
→ открывает краткое объяснение
```

---

## 17. Визуальное время и расчётное время

UI должен явно различать:

```text
скорость анимации
```

и:

```text
расчётную продолжительность рабочего цикла
```

Например:

```text
Анимация: 2×
Расчётное время цикла: 24 с
```

Изменение скорости воспроизведения не должно менять расчёт.

---

## 18. Экран «Параметры»

Параметры должны группироваться смыслово.

Для экскаватора:

```text
Рабочий орган
- Вместимость ковша
- Коэффициент наполнения

Цикл
- Продолжительность рабочего цикла

Использование времени
- Коэффициент использования рабочего времени
```

Для каждого параметра:

- название;
- значение;
- единица;
- короткое объяснение;
- источник/тип значения при необходимости.

---

## 19. Экран «Производительность»

Рекомендуемый layout:

```text
┌─────────────────────┬───────────────────────────────┐
│ Parameters          │ Result                        │
│                     │                               │
│ bucket capacity     │ Q = ... м³/ч                 │
│ fill factor         │                               │
│ cycle time          │ Why?                         │
│ time utilization    │ short explanation            │
└─────────────────────┴───────────────────────────────┘
```

Главный UX-принцип:

> Результат всегда должен сопровождаться объяснением.

---

## 20. Изменение параметров

При изменении параметра:

1. значение обновляется;
2. расчёт пересчитывается;
3. изменившиеся результаты подсвечиваются;
4. система показывает направление изменения;
5. при необходимости даётся короткое объяснение.

Пример:

```text
Время цикла:
24 → 30 с

Производительность:
134.5 → 107.6 м³/ч

Причина:
за один час выполняется меньше рабочих циклов.
```

---

## 21. Прогноз до расчёта

Желательный учебный режим:

```text
Что произойдёт с производительностью?
[увеличится]
[уменьшится]
[не изменится]
```

После ответа:

```text
→ пересчитать
→ показать результат
→ объяснить
```

Это не обязательно для первого технического vertical slice, но должно учитываться в UX.

---

## 22. Экран «Где применяется»

Содержит связанные процессы.

Для MVP:

```text
Разработка грунта с погрузкой в автосамосвалы и транспортированием
```

Карточка процесса:

- название;
- схема;
- роль текущей машины;
- действие:

```text
Перейти к процессу
```

---

## 23. Каталог процессов

Первый MVP:

```text
Земляные работы
└── Разработка и транспортирование грунта
```

Карточка процесса должна отвечать:

- что происходит;
- какой результат;
- какие машины участвуют;
- сколько этапов.

---

## 24. Экран технологического процесса

Главная зона должна показывать последовательность:

```text
Разработка
→ Погрузка
→ Транспортирование
→ Разгрузка
```

Каждый этап кликабелен.

Активный этап показывает:

- назначение;
- вход;
- выход;
- участвующие машины;
- ключевые параметры.

---

## 25. Визуализация процесса

Для первого MVP допускаются два режима.

### Режим 1 — Схема

```text
[Экскаватор]
    ↓
Разработка / Погрузка
    ↓
[Автосамосвал]
    ↓
Транспортирование
    ↓
Разгрузка
```

### Режим 2 — 3D-сцена

Упрощённая площадка:

- экскаватор;
- зона разработки;
- автосамосвал;
- маршрут;
- зона разгрузки.

Первый vertical slice может начинаться со схемы и позднее получить 3D-сцену.

---

## 26. Краткая карточка машины внутри процесса

При клике на машину открывается compact card.

Пример:

```text
Гидравлический экскаватор

Роль:
разработка грунта и загрузка транспорта.

Ключевые параметры:
1.2 м³ — ковш
24 с — цикл

[Изучить машину]
```

Карточка должна закрываться без изменения текущего этапа.

---

## 27. Полный переход в машину

Кнопка:

```text
Изучить машину
```

открывает полноценный учебный модуль.

UI должен показывать контекст:

```text
Вы изучаете экскаватор из этапа «Разработка грунта»
```

или хотя бы обеспечивать явный возврат:

```text
← Назад к этапу «Разработка грунта»
```

---

## 28. Экран производственной системы

Цель:

> Показать экскаватор и автосамосвалы как единый комплекс.

Главные блоки:

```text
Состав комплекса
Параметры
Визуализация
Результаты
```

---

## 29. Состав комплекса

Пользователь видит:

```text
Экскаватор × 1
Автосамосвал × N
```

Для MVP меняется только `N`.

Control:

```text
[-] 3 [+]
```

или slider/stepper.

Для дискретного количества техники предпочтителен stepper.

---

## 30. Основные результаты производственной системы

На экране должны быть видны минимум:

```text
Производительность комплекса
Загрузка экскаватора
Простой экскаватора
Ожидание самосвалов
Продолжительность работ
Эксплуатационные затраты
```

Не следует показывать все показатели одновременно как одинаково важные.

---

## 31. Иерархия результатов

### Primary

```text
Производительность
Продолжительность
Стоимость
```

### Secondary

```text
Загрузка экскаватора
Простой
Ожидание транспорта
Match factor
```

Match factor является объяснительным техническим показателем и не должен быть главным KPI для студента начального уровня.

---

## 32. Карточка KPI

Пример:

```text
Производительность комплекса

123.2 м³/ч

↑ +50% относительно варианта с 2 самосвалами

Почему:
экскаватор почти полностью обеспечен транспортом.
```

Сравнение появляется только если существует baseline.

---

## 33. Визуализация простоя

Простой должен быть виден не только числом.

Например:

```text
Работа экскаватора

███████████████████░ 99%
```

или:

```text
Работа   99%
Простой   1%
```

Для автосамосвалов:

```text
Движение / обслуживание / ожидание
```

---

## 34. Эксперимент с количеством автосамосвалов

Пользователь должен пройти простой цикл:

```text
1. выбрать N
2. увидеть прогноз/ожидание
3. запустить расчёт
4. получить результаты
5. изменить N
6. сравнить
```

Изменение `N` не должно автоматически стирать предыдущий вариант, если пользователь выбрал «Сохранить для сравнения».

---

## 35. Сравнение сценариев

Экран сравнения должен позволять минимум два варианта.

Пример:

```text
Вариант A: 3 самосвала
Вариант B: 4 самосвала
```

Таблица:

| Показатель | A | B | Изменение |
|---|---:|---:|---:|
| Производительность | | | |
| Простой экскаватора | | | |
| Ожидание транспорта | | | |
| Продолжительность | | | |
| Стоимость | | | |

---

## 36. Интерпретация сравнения

Система может показывать нейтральные факты:

```text
+1 автосамосвал:
- снизил простой экскаватора;
- увеличил производительность на X%;
- увеличил стоимость часа комплекса;
- увеличил ожидание транспорта.
```

Система не должна автоматически говорить:

```text
Это лучший вариант
```

если критерий оптимальности явно не задан.

---

## 37. Учебное задание

Задание показывается как отдельный режим.

Пример:

```text
Задача

Необходимо выполнить 1000 м³ земляных работ.

Исследуйте несколько вариантов количества автосамосвалов
и выберите вариант, который вы считаете рациональным.

Обоснуйте решение.
```

---

## 38. Ответ студента

Для MVP достаточно:

```text
Выбранный сценарий
+
краткое текстовое объяснение
```

Например:

```text
Я выбираю 3 автосамосвала, потому что ...
```

Автоматическая AI-оценка объяснения не входит в MVP.

---

## 39. Система подсказок

Подсказки должны быть контекстными.

Пример:

Если пользователь выбрал 1 самосвал:

```text
Экскаватор простаивает значительную часть времени.

Попробуйте определить, какое звено ограничивает систему.
```

Не следует сразу писать:

```text
Добавьте ещё 2 самосвала.
```

---

## 40. Система ошибок

### Domain validation error

Пример:

```text
Скорость должна быть больше 0 км/ч.
```

### Loading error

```text
Не удалось загрузить 3D-модель.
Учебный текст и расчёты остаются доступны.
```

### Simulation error

```text
Расчёт не выполнен.
Проверьте исходные параметры.
```

Не показывать пользователю stack trace.

---

## 41. Loading состояния

Для 3D:

```text
Загрузка модели...
```

с индикатором.

Если возможно:

```text
Загружено 68%
```

Контент страницы должен появляться раньше 3D, если это технически возможно.

---

## 42. Empty states

Если у машины пока нет связанного процесса:

```text
Связанные процессы пока не добавлены.
```

Не нужно скрывать раздел полностью, если это создаёт непонятную навигацию.

---

## 43. Responsive behavior

### Desktop

Основной целевой режим MVP.

Рекомендуется:

```text
3D/scene + side panel
```

### Tablet

Допускается:

```text
main view
+
drawer / collapsible panel
```

### Mobile

MVP не обязан обеспечивать полноценный сложный 3D workflow на телефоне.

Минимум:

- страницы читаемы;
- навигация работает;
- расчёты работают;
- 3D не ломает страницу.

Полноценная mobile UX может быть отдельной фазой.

---

## 44. Accessibility

Минимальные требования:

- управление без обязательного hover;
- keyboard focus для основных controls;
- достаточный contrast;
- текст не должен существовать только внутри canvas;
- 3D-информация должна иметь текстовую альтернативу;
- выбранный элемент должен отображаться не только цветом;
- controls должны иметь понятные labels;
- анимацию можно поставить на паузу.

---

## 45. Motion

Анимация должна помогать пониманию.

Не допускаются:

- декоративные постоянные движения;
- избыточные camera fly-through;
- резкие автоматические повороты;
- невозможность остановить учебную анимацию.

Camera transition при выборе узла должна быть короткой и ненавязчивой.

---

## 46. Цветовая семантика

Цвет не должен быть единственным носителем смысла.

Рекомендуемые семантические категории:

```text
active
selected
positive change
negative change
warning
neutral
```

Конкретная палитра определяется позже.

---

## 47. Формулы

Формула должна показываться по запросу или рядом с расчётом, но не доминировать над интерфейсом.

Пример:

```text
Как рассчитано?
```

раскрывает:

```text
Q = q × k × 3600 / t × ...
```

и краткое объяснение параметров.

Главная цель — понимание зависимости, а не чтение математической записи.

---

## 48. Units

Единица должна отображаться рядом со значением.

Правильно:

```text
24 с
2.0 км
123.2 м³/ч
```

Нежелательно:

```text
24
2.0
123.2
```

с единицей только в заголовке далеко от значения.

---

## 49. Illustrative data

Если параметр является учебным, интерфейс должен позволять явно это обозначить.

Например tooltip:

```text
Учебное значение.
Не является характеристикой конкретной модели техники.
```

Это особенно важно для:

- стоимости машино-часа;
- скоростей;
- времени цикла;
- вместимости;
- других параметров, которые пользователь может принять за реальные справочные данные.

---

## 50. Source / provenance

В будущем рядом с реальными техническими данными может отображаться:

```text
Источник
```

В MVP архитектура UI должна позволять такую метаинформацию, даже если большинство данных пока illustrative.

---

## 51. URL / deep-link requirements

Желательно, чтобы ключевые сущности имели устойчивые URL.

Пример:

```text
/machines/excavator
/processes/excavation-haul
/systems/excavator-haul-system
```

Конкретная структура маршрутов выбирается архитектурой приложения.

Главное требование:

- сущность должна быть доступна по прямой ссылке;
- контекстный возврат должен работать независимо от deep-link.

---

## 52. State preservation

При переходе:

```text
процесс → машина → назад
```

желательно сохранять:

- активный этап;
- выбранную машину;
- открытый panel;
- при возможности camera state.

При переходе между страницами эксперимента желательно сохранять:

- текущие параметры;
- сохранённые comparison scenarios.

---

## 53. Reset

Для интерактивных модулей должны существовать явные действия:

```text
Сбросить параметры
Сбросить камеру
Перезапустить цикл
Вернуть базовый сценарий
```

Они не должны быть объединены в одну опасную кнопку «Сбросить всё», если это разрушает пользовательский контекст.

---

## 54. First vertical slice — UI scope

Первый vertical slice должен реализовать только:

1. главную страницу;
2. каталог машин;
3. страницу экскаватора;
4. интерактивную 3D-модель;
5. выбор хотя бы одного компонента — `bucket`;
6. карточку компонента;
7. рабочий цикл Play/Pause;
8. раздел «Где применяется»;
9. переход в процесс;
10. страницу процесса;
11. выбор этапа `excavation-stage`;
12. compact card экскаватора;
13. переход обратно в полный модуль;
14. контекстный возврат.

Расчёт fleet simulation может появиться следующим slice.

---

## 55. Second vertical slice — simulation scope

После подтверждения первого slice:

1. экран производственной системы;
2. ввод `truck-count`;
3. расчёт по `earthworks-deterministic-v1`;
4. основные KPI;
5. объяснение результатов;
6. сохранение двух сценариев;
7. сравнение.

---

## 56. Не требуется в MVP UI

Не проектировать сейчас:

- личный кабинет;
- регистрацию;
- роли пользователей;
- админ-панель;
- LMS dashboard;
- журнал оценок;
- сложный onboarding;
- глобальный поиск;
- комментарии;
- социальные функции;
- AI chat;
- AR;
- VR;
- мультиязычный UI;
- полноценный mobile-first режим;
- сложный редактор учебного контента.

---

## 57. Design system — минимальный уровень

До появления полноценного design system достаточно определить базовые primitives:

```text
Button
IconButton
Tabs
Card
Panel
Drawer
Tooltip
Slider
Stepper
Input
MetricCard
Callout
Breadcrumbs
Modal
LoadingState
ErrorState
```

Codex не должен создавать огромную UI-библиотеку заранее.

---

## 58. UX acceptance criteria

UX первого MVP считается состоятельным, если пользователь без инструкции способен:

- понять, как начать с машины;
- открыть экскаватор;
- вращать модель;
- выбрать ковш;
- понять его назначение;
- запустить рабочий цикл;
- перейти в связанный процесс;
- выбрать этап;
- открыть экскаватор из процесса;
- вернуться в тот же этап;
- изменить количество автосамосвалов;
- увидеть изменение результатов;
- сравнить два варианта;
- объяснить, почему результаты отличаются.

---

## 59. UI quality bar

Интерфейс MVP должен восприниматься как учебная лаборатория, а не как:

- сайт-каталог;
- 3D showcase;
- dashboard ради dashboard;
- набор случайных sliders;
- игровая сцена без объяснений.

Каждый интерактивный элемент должен отвечать хотя бы на один вопрос:

```text
Что это?
Как это работает?
От чего зависит?
Где применяется?
Что изменится, если...?
Почему получился такой результат?
Какое решение можно принять?
```

---

## 60. Главная UX-формула

```text
Object
→ Interaction
→ Explanation
→ Experiment
→ Result
→ Interpretation
→ Decision
```

Каждый важный экран MVP должен поддерживать хотя бы часть этой цепочки.
