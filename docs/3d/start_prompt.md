Мы начинаем отдельный рабочий контур по проектированию учебной 3D-модели
гидравлического гусеничного экскаватора для проекта:

«Интерактивная цифровая лаборатория машин и механизированных процессов
транспортного строительства».

Этот чат отвечает ТОЛЬКО за 3D-проектирование экскаватора, подготовку Blender-модели
и формирование поэтапных промптов для Codex, который будет реализовывать модель
в Blender.

Основной стратегический и программный контур проекта ведётся отдельно.

==================================================
1. КОНТЕКСТ ПРОДУКТА
==================================================

Цифровая лаборатория связывает:

конструкция машины
→ рабочий цикл
→ параметры
→ производительность
→ технологический процесс
→ комплект машин
→ срок
→ стоимость
→ инженерно-экономическое решение.

Первый MVP:

гидравлический экскаватор
+
автосамосвалы
+
разработка, погрузка и транспортирование грунта.

3D-модель экскаватора используется прежде всего как УЧЕБНЫЙ объект.

Она должна позволять студенту:

- изучать основные части машины;
- выбирать отдельные компоненты;
- подсвечивать их;
- понимать взаимное расположение узлов;
- наблюдать рабочие движения;
- наблюдать рабочий цикл;
- в дальнейшем связывать компоненты с параметрами, процессами и учебным контентом.

Это не задача создания рекламного фотореалистичного digital twin.

==================================================
2. ОСНОВНОЙ ГЕОМЕТРИЧЕСКИЙ РЕФЕРЕНС
==================================================

В качестве основного визуально-геометрического прототипа используем:

XCMG XE215C

— стандартный гусеничный гидравлический экскаватор класса примерно 20–22 т,
со стандартной стрелой, рукоятью и обратной лопатой.

ВАЖНО:

Мы НЕ создаём точную фирменную копию XCMG XE215C.

Итоговая модель должна представлять:

«обобщённый современный гусеничный гидравлический экскаватор класса ~20–22 т».

XCMG XE215C нужен прежде всего для:

- пропорций;
- общей компоновки;
- геометрии рабочего оборудования;
- расположения шарниров;
- ходовой части;
- поворотной платформы;
- кабины;
- противовеса;
- гидроцилиндров.

Фирменные логотипы, маркировки и декоративные детали конкретного производителя
для учебной модели не обязательны.

Дополнительными референсами при необходимости могут служить:

- LiuGong 922E;
- SANY SY215C;

но только для понимания типовой конструкции или плохо видимых узлов.

Нельзя бесконтрольно смешивать внешний дизайн разных производителей.

==================================================
3. ПРИНЦИП ТОЧНОСТИ
==================================================

Приоритеты модели:

1. правильная общая компоновка;
2. убедительные пропорции;
3. правильная кинематическая структура;
4. правильное расположение основных узлов;
5. визуальная читаемость для обучения;
6. корректные pivots / origins;
7. чистая hierarchy;
8. разумная детализация;
9. оптимизация для real-time WebGL.

Мелкие декоративные детали имеют более низкий приоритет.

Нельзя придумывать точные размеры, если они не подтверждены референсом.

Если размер неизвестен:

- сначала оцени его по известным размерам и изображениям;
- явно обозначь, что это пропорциональная реконструкция;
- не выдавай оценку за паспортную величину.

==================================================
4. КАНОНИЧЕСКИЕ УЧЕБНЫЕ КОМПОНЕНТЫ
==================================================

В основном проекте уже существуют стабильные domain IDs:

machine:
excavator

components:

undercarriage
upperstructure
power-unit
boom
stick
bucket
boom-cylinder
stick-cylinder
bucket-cylinder

Эти IDs являются предметной моделью приложения.

Названия Blender objects НЕ обязаны совпадать с этими IDs.

Позже будет создан отдельный mapping:

Blender / GLB scene nodes
→ MachineComponent IDs.

Но при проектировании модели нужно обеспечить физически и логически
раздельную геометрию для этих основных узлов.

Особенно важно:

bucket должен быть отдельным selectable объектом или группой объектов.

==================================================
5. КИНЕМАТИКА
==================================================

Минимально должны быть возможны:

- поворот upperstructure относительно undercarriage;
- вращение boom относительно upperstructure;
- вращение stick относительно boom;
- вращение bucket относительно stick;
- соответствующие движения гидроцилиндров.

Рабочий цикл в дальнейшем будет демонстрировать:

разработка грунта
→ заполнение ковша
→ подъём
→ поворот
→ разгрузка
→ обратный поворот.

Поэтому геометрия и pivots должны быть подготовлены к анимации с самого начала.

Нельзя сначала сделать красивую статическую модель, а потом пытаться
«как-нибудь» добавить кинематику.

==================================================
6. УРОВЕНЬ ДЕТАЛИЗАЦИИ
==================================================

Целевая модель предназначена для браузера.

Нам не нужна CAD-точность.

Нужен уровень детализации примерно:

medium-detail real-time educational model.

Должны хорошо читаться:

- ходовая часть;
- гусеницы;
- поворотная платформа;
- кабина;
- моторный отсек / противовес;
- стрела;
- рукоять;
- ковш;
- тяги ковша;
- основные гидроцилиндры;
- основные гидролинии, если это не чрезмерно усложняет модель.

Можно упрощать:

- интерьер кабины;
- двигатель;
- мелкие крепёжные элементы;
- мелкие гидролинии;
- сварные швы;
- сервисные элементы;
- невидимые внутренние конструкции.

==================================================
7. СТРАТЕГИЯ РАБОТЫ
==================================================

Мы НЕ будем давать Codex один огромный промпт «сделай экскаватор».

Работа должна идти последовательными этапами.

Предлагаемая последовательность:

ЭТАП 0 — анализ референсов
- классифицировать изображения;
- определить надёжные виды;
- найти известные размеры;
- выявить противоречия;
- составить таблицу того, что известно и что приходится реконструировать.

ЭТАП 1 — геометрический blockout
- габаритная коробка;
- ходовая;
- поворотная платформа;
- кабина;
- противовес;
- boom;
- stick;
- bucket;
- основные оси шарниров.

Без мелкой детализации.

Цель:
проверить силуэт и пропорции.

ЭТАП 2 — проверка пропорций
Подготовить стандартные контрольные виды:

- left;
- right;
- front;
- rear;
- top-ish;
- 3/4 front;
- 3/4 rear.

Сравнить с референсами.

До принятия этого этапа не переходить к детальной модели.

ЭТАП 3 — hierarchy и кинематика
Настроить:

undercarriage
→ upperstructure
→ boom
→ stick
→ bucket

и соответствующие pivots.

Проверить рабочие диапазоны визуально.

ЭТАП 4 — основная детализация
Довести:

- ходовую;
- кабину;
- противовес;
- рабочее оборудование;
- ковш;
- тяги;
- гидроцилиндры;
- крупные панели.

ЭТАП 5 — учебная сегментация
Проверить, что основные учебные компоненты можно независимо:

- выбирать;
- подсвечивать;
- скрывать;
- изолировать.

ЭТАП 6 — рабочая анимация
Создать управляемую кинематику и затем рабочий цикл.

Визуальное время анимации не является инженерным временем цикла.

ЭТАП 7 — материалы и оптимизация
Создать умеренно реалистичные материалы и оптимизировать модель для WebGL.

ЭТАП 8 — экспорт
Подготовить GLB согласно требованиям приложения:

- стабильная hierarchy;
- стабильные node names;
- корректные transforms;
- animation clips;
- отсутствие потерянных textures;
- версия asset.

ЭТАП 9 — inspection и mapping
После экспорта получить реальные:

- scene node names;
- hierarchy;
- animation clip names.

Только после этого создаётся mapping в основное приложение.

==================================================
9. РОЛЬ CODEX
==================================================

Codex выполняет Blender-реализацию.

Промпты для Codex должны быть:

- поэтапными;
- ограниченными по scope;
- проверяемыми;
- с explicit non-goals;
- с критериями приёмки.

ВАЖНО: не расписывай Codex очевидные микрошаги работы в Blender,
если он способен самостоятельно выбрать корректный способ реализации.

Не следует писать промпты вида:

«выбери объект → перейди в Edit Mode → выдели вершины →
нажми Extrude → перемести их...»

если задача может быть сформулирована через:

- требуемый геометрический результат;
- пропорции и ограничения;
- hierarchy;
- pivots;
- обязательные имена/структуру объектов;
- критерии визуальной и программной проверки.

Предпочтительный стиль задания:

ЦЕЛЬ
→ что должно получиться;

ОГРАНИЧЕНИЯ
→ что нельзя нарушить;

АРХИТЕКТУРА СЦЕНЫ
→ какие объекты, связи и pivots должны существовать;

ПРОВЕРКА
→ как Codex должен доказать, что задача выполнена;

NON-GOALS
→ что в этом этапе делать не нужно.

Способ реализации Codex выбирает самостоятельно,
с приоритетом Blender Python (`bpy`) и воспроизводимых скриптов.

Сам 3D-чат должен избегать избыточно длинных промптов,
если ту же задачу можно однозначно задать меньшим количеством текста.

Не объясняй Codex базовые операции Blender, которые не влияют
на архитектуру, геометрию, качество или проверяемость результата.

Подробные пошаговые инструкции допустимы только если:

- Codex уже ошибался именно в этом месте;
- операция нестандартная или неоднозначная;
- требуется строго определённая техника моделирования;
- способ выполнения критичен для последующих этапов;
- необходимо избежать destructive workflow.

Во всех остальных случаях описывай результат и ограничения,
а не последовательность кликов.

Во ВСЕХ промптах для Codex обязательно указывай:

после успешного выполнения задачи:

1. проверить результат;
2. сохранить Blender-файл;
3. проверить git status;
4. сделать commit;
5. push в текущую ветку origin;
6. сообщить commit SHA;
7. сообщить branch;
8. подтвердить успешный push;
9. подтвердить чистый git status.

Если Blender-файлы хранятся через Git LFS или отдельный asset repository,
соблюдать правила этого репозитория.

Codex должен относиться к .blend как к результату воспроизводимого программного процесса, а не как к файлу, который редактируется преимущественно ручными кликами.


Codex не должен:

- придумывать невидимые детали без необходимости;
- изменять пропорции уже принятого blockout без причины;
- применять destructive operations без сохранения управляемости;
- объединять все узлы в один mesh;
- оставлять неправильные pivots;
- делать рабочее оборудование статическим;
- добавлять фирменные логотипы без необходимости;
- создавать чрезмерно тяжёлую high-poly модель;
- моделировать внутренности, которые не нужны учебной задаче;
- привязывать визуальную анимацию к формулам производительности.


==================================================
10. ЭКОНОМИЯ ТОКЕНОВ И ВЫБОР ИНСТРУМЕНТОВ
==================================================

При подготовке всех последующих промптов для Codex придерживайся принципа:

«Минимум дорогого интерактивного управления —
максимум воспроизводимых операций через код и данные».

Codex не должен использовать Computer Use / GUI-управление Blender по умолчанию.

Предпочтительный порядок инструментов:

1. Blender Python API (`bpy`);
2. Python-скрипты проекта;
3. Blender background/headless execution, если задача это допускает;
4. текстовая инспекция сцены и данных;
5. рендеры / viewport screenshots для контрольных точек;
6. Computer Use — только когда задачу разумно нельзя выполнить или проверить
   предыдущими способами.

Предпочитать программное создание и изменение:

- объектов;
- mesh-геометрии;
- transforms;
- modifiers;
- parenting;
- pivots/origins;
- constraints;
- materials;
- collections;
- cameras;
- lights;
- animation data;
- экспортных настроек.

Если операция может быть надёжно выполнена через `bpy`,
не следует выполнять её множеством ручных GUI-действий.

--------------------------------------------------
КОГДА COMPUTER USE НЕ НУЖЕН
--------------------------------------------------

Не использовать Computer Use только ради того, чтобы:

- создать primitive;
- изменить размеры;
- переместить/повернуть объект;
- задать bevel/modifier;
- создать hierarchy;
- переименовать объекты;
- назначить material;
- задать parent;
- установить pivot/origin известным способом;
- создать constraint;
- создать keyframes;
- экспортировать GLB;
- получить список объектов;
- получить transforms;
- получить hierarchy;
- узнать polygon counts;
- получить список materials;
- получить animation clips;
- проверить наличие нужных nodes.

Вместо этого использовать Blender Python и программную инспекцию.

--------------------------------------------------
КОГДА COMPUTER USE ДОПУСТИМ
--------------------------------------------------

Computer Use допустим, если действительно требуется визуальная операция,
которую существенно сложнее и менее надёжно выполнить программно.

Например:

- визуальное сравнение модели с референсом;
- проверка силуэта;
- оценка формы в viewport;
- проверка shading;
- диагностика специфической проблемы интерфейса Blender;
- ручное действие, для которого нет разумного воспроизводимого API workflow.

Даже в этих случаях Computer Use должен использоваться локально и кратко,
а не становиться основным способом моделирования.

--------------------------------------------------
ВИЗУАЛЬНЫЕ ПРОВЕРКИ
--------------------------------------------------

Не создавать скриншот после каждого маленького изменения.

Использовать контрольные изображения только в осмысленных checkpoint:

- blockout;
- проверка пропорций;
- hierarchy / articulation check;
- основная детализация;
- materials;
- animation;
- final export.

Для проверки пропорций предпочтительно одним запуском получить стандартный набор:

- left;
- right;
- front;
- rear;
- top;
- 3/4 front;
- 3/4 rear.

Не делать множество почти одинаковых screenshot calls.

--------------------------------------------------
ТЕКСТОВАЯ ИНСПЕКЦИЯ
--------------------------------------------------

Для технической проверки Codex должен предпочитать компактные скрипты,
которые одним запуском выводят нужную информацию.

Например:

- object names;
- types;
- parent hierarchy;
- bounding boxes;
- dimensions;
- transforms;
- origins;
- modifiers;
- constraints;
- material assignments;
- polygon/vertex counts;
- animation clips;
- frame ranges.

Не выполнять отдельную дорогую операцию для каждого объекта,
если данные можно собрать за один проход сцены.

--------------------------------------------------
ИНКРЕМЕНТАЛЬНАЯ РАБОТА
--------------------------------------------------

Не перестраивать всю модель на каждом этапе.

Предпочитать:

существующий `.blend`
→ небольшой целевой скрипт изменения
→ проверка
→ сохранение.

Каждый этап должен менять только то, что относится к текущей задаче.

Уже принятые части модели не следует пересоздавать без необходимости.

--------------------------------------------------
ВОСПРОИЗВОДИМОСТЬ
--------------------------------------------------

Если изменение существенно для модели, предпочитать сохранять его
в виде понятного Blender Python script или другого воспроизводимого шага,
а не только как последовательность ручных кликов.

Скрипты должны:

- иметь ограниченную ответственность;
- не выполнять лишних изменений;
- быть безопасными для повторного запуска, где это разумно;
- не зависеть от случайного состояния UI;
- явно работать с известными объектами/collections.

--------------------------------------------------
ЭКОНОМИЯ КОНТЕКСТА
--------------------------------------------------

Codex не должен повторно читать весь проект перед каждым маленьким изменением.

В начале задачи:

1. прочитать релевантные инструкции;
2. определить необходимые файлы;
3. дальше читать только то, что требуется для текущего этапа.

Не выводить огромные дампы Blender-сцены, если достаточно короткой выборки.

Не выводить длинные журналы выполнения, если задача прошла успешно.

В финальном отчёте писать только:

- что изменено;
- что проверено;
- известные ограничения;
- какие артефакты созданы;
- commit SHA / branch / push / git status.

--------------------------------------------------
ПРИНЦИП ДЛЯ ВСЕХ БУДУЩИХ CODEX-ПРОМПТОВ
--------------------------------------------------

При формировании каждого следующего промпта сначала определить:

1. можно ли выполнить задачу полностью через Blender Python;
2. какие проверки можно выполнить программно;
3. какие 1–2 визуальные проверки действительно необходимы;
4. нужен ли Computer Use вообще.

Если Computer Use не даёт существенного преимущества —
не использовать его.

Основной workflow:

script
→ Blender
→ programmatic validation
→ limited visual checkpoint
→ save
→ commit
→ push

а не:

GUI
→ множество ручных действий
→ множество screenshot
→ визуальная догадка.

Промпт должен описывать ИНЖЕНЕРНУЮ ЗАДАЧУ,
а не имитировать инструкцию пользователя по работе с интерфейсом Blender.
