## 1. Назначение документа

Этот документ фиксирует основные пользовательские маршруты первого MVP.

Цель — определить не визуальный дизайн экранов, а логику перемещения пользователя между учебными контекстами:

- машиной;
- технологическим процессом;
- производственной системой;
- расчётом;
- экспериментом;
- учебными заданиями.

Ключевой принцип:

> Пользователь должен иметь возможность начать обучение как с машины, так и с технологического процесса, при этом обе траектории должны приводить к одной и той же предметной модели.

---

## 2. Базовые принципы навигации

### 2.1. Два равноправных входа

На верхнем уровне MVP должны существовать как минимум два равноправных входа:

- **Машины**
- **Процессы**

Ни один из них не является «основным», а второй — вспомогательным.

---

### 2.2. Контекст должен сохраняться

Если пользователь перешёл:

```text
Процесс
→ Этап процесса
→ Машина
→ Учебный модуль машины
```

то возврат должен приводить его:

```text
обратно к тому же этапу процесса
```

а не на главную страницу.

---

### 2.3. Одна сущность — разные представления

Экскаватор, открытый из каталога машин, и экскаватор, открытый из технологического процесса, — это одна и та же предметная сущность.

Различаться может только контекст отображения.

---

### 2.4. Краткая карточка и полный модуль

При переходе из процесса к машине пользователь не всегда должен покидать процесс.

Сначала может открываться контекстная карточка машины:

- название;
- назначение;
- ключевая роль в текущем процессе;
- основные параметры;
- кнопка «Изучить машину».

Только после явного действия пользователь переходит в полный учебный модуль.

---

### 2.5. Переходы должны быть объяснимыми

Каждый переход между разделами должен иметь предметный смысл.

Пример:

```text
Экскаватор
→ Где применяется
→ Разработка грунта
```

лучше, чем:

```text
Экскаватор
→ Другие разделы
→ Процессы
```

---

## 3. Верхнеуровневая структура MVP

```text
Главная
├── Машины
│   ├── Экскаватор
│   └── Автосамосвал
│
├── Процессы
│   └── Земляные работы
│       └── Разработка и транспортирование грунта
│
└── Производственная система
    └── Экскаватор + автосамосвалы
```

Раздел «Производственная система» может быть доступен как:

- самостоятельная точка входа;
- следующий уровень после машины;
- следующий уровень после процесса.

Раздел «Производственная система» является самостоятельным учебным контекстом полного MVP и появляется во втором vertical slice. В первый технический vertical slice по `docs/design/ui-ux-spec.md` §54 fleet simulation не входит.

## 4. Flow A — От машины к процессу

### Цель

Пользователь начинает с технического объекта и постепенно переходит к пониманию его роли в производственной системе.

### Основной маршрут

```text
Главная
→ Машины
→ Экскаватор
→ Обзор
→ Конструкция
→ Рабочий цикл
→ Производительность
→ Где применяется
→ Разработка и транспортирование грунта
→ Производственная система
→ Эксперимент
→ Сравнение вариантов
```

---

### A1. Главная → Машины

Пользователь выбирает вход **«Машины»**.

Система показывает список доступных объектов MVP.

Для первой версии:

- гидравлический экскаватор;
- автосамосвал.

Экскаватор отображается как основной глубоко проработанный объект.

---

### A2. Машины → Экскаватор

При выборе экскаватора открывается его учебный модуль.

Стартовый экран должен отвечать на вопросы:

- что это за машина;
- для чего применяется;
- какие основные операции выполняет;
- какие учебные разделы доступны.

Основные вкладки:

```text
Обзор
Конструкция
Как работает
Рабочий цикл
Параметры
Производительность
Где применяется
```

---

### A3. Экскаватор → Конструкция

Пользователь открывает 3D-модель.

Доступные действия:

- вращение;
- масштабирование;
- выбор узла;
- подсветка;
- отображение названия;
- отображение краткого назначения.

При выборе узла интерфейс показывает контекстную информацию.

Пример:

```text
Ковш

Назначение:
разработка и захват грунта.

Связан с:
рабочим циклом;
вместимостью ковша;
коэффициентом наполнения.
```

---

### A4. Конструкция → Рабочий цикл

Пользователь запускает демонстрацию рабочего цикла.

Система показывает фазы:

```text
разработка грунта
→ заполнение ковша
→ подъём
→ поворот
→ разгрузка
→ обратный поворот
```

Пользователь может:

- запускать;
- ставить на паузу;
- переходить между фазами;
- изменять скорость воспроизведения;
- видеть текущую фазу.

---

### A5. Рабочий цикл → Производительность

После знакомства с циклом пользователь переходит к расчётному уровню.

Система показывает связь:

```text
объём за цикл
+
продолжительность цикла
+
коэффициенты использования
→ производительность
```

Пользователь изменяет один параметр и наблюдает результат.

---

### A6. Производительность → Где применяется

Пользователь переходит к разделу применения машины.

Система показывает связанные технологические процессы.

В MVP доступен один основной процесс:

**Разработка грунта с погрузкой в автосамосвалы и транспортированием.**

Пользователь выбирает его.

---

### A7. Машина → Процесс

Переход должен сохранять происхождение пользователя.

Система должна понимать:

```text
sourceContext = machine
sourceEntity = excavator
```

После открытия процесса интерфейс может показать:

> Вы перешли сюда из модуля «Экскаватор».

Это не обязательно должно быть текстом на экране, но контекст должен сохраняться в состоянии приложения.

---

### A8. Процесс → Производственная система

Пользователь видит технологическую последовательность:

```text
разработка
→ погрузка
→ транспортирование
→ разгрузка
```

После этого переходит к сценарию совместной работы:

```text
1 экскаватор
+
N автосамосвалов
```

---

### A9. Производственная система → Эксперимент

Пользователь изменяет количество автосамосвалов.

Система пересчитывает:

- загрузку экскаватора;
- простой экскаватора;
- ожидание транспорта;
- производительность комплекса;
- продолжительность работ;
- эксплуатационные затраты.

---

### A10. Эксперимент → Сравнение вариантов

Пользователь может сравнить минимум два сценария.

Пример:

```text
2 самосвала
vs
3 самосвала
```

Система показывает различия.

Цель — не выдать «правильный ответ», а дать возможность обосновать решение.

---

## 5. Flow B — От процесса к машине

### Цель

Пользователь начинает с производственной задачи и изучает технику по мере необходимости.

### Основной маршрут

```text
Главная
→ Процессы
→ Земляные работы
→ Разработка и транспортирование грунта
→ Этап «Разработка»
→ Экскаватор
→ Краткая карточка
→ Полный учебный модуль
→ Возврат в процесс
→ Производственная система
```

---

### B1. Главная → Процессы

Пользователь выбирает **«Процессы»**.

Система показывает доступные категории.

В MVP:

```text
Земляные работы
```

---

### B2. Земляные работы → Процесс

Открывается процесс:

**Разработка грунта с погрузкой в автосамосвалы и транспортированием.**

Пользователь видит общую технологическую цепочку.

---

### B3. Выбор этапа

Пользователь выбирает этап:

**Разработка грунта**

Система показывает:

- назначение этапа;
- входной результат;
- выходной результат;
- используемые машины;
- ключевые параметры.

Для этапа отображается экскаватор.

---

### B4. Этап → Краткая карточка машины

При выборе экскаватора не требуется немедленно уходить со страницы процесса.

Открывается краткая карточка:

```text
Гидравлический экскаватор

Роль:
разработка грунта и загрузка автосамосвала.

Ключевые параметры:
- вместимость ковша;
- время цикла;
- коэффициент наполнения.

[Изучить машину]
```

---

### B5. Краткая карточка → Полный модуль машины

Если пользователь выбирает «Изучить машину», открывается полноценный модуль экскаватора.

При этом приложение сохраняет:

```text
returnContext = process
processId = excavation-haul
stageId = excavation-stage
```

Идентификаторы `processId` и `stageId` должны быть адресуемы в URL и сохраняться при переходах внутри модуля машины. Контекстный возврат не должен зависеть только от browser history или от `sessionStorage`; восстановление дополнительных панелей и камеры через storage необязательно и отложено.

---

### B6. Изучение машины

Пользователь может открыть:

- конструкцию;
- рабочий цикл;
- параметры;
- производительность.

Он не обязан проходить весь модуль.

---

### B7. Возврат в процесс

При выборе действия «Назад к процессу» пользователь возвращается:

```text
Разработка и транспортирование грунта
→ этап «Разработка грунта»
```

Выбранный этап должен остаться активным.

Если возможно, сохраняется также положение интерфейса и камеры.

---

## 6. Flow C — Быстрый контекстный просмотр машины

### Цель

Дать пользователю минимальную справку без смены основного контекста.

```text
Процесс
→ Этап
→ Машина
→ Краткая карточка
→ Закрыть
→ Тот же этап процесса
```

Карточка должна быть достаточной, если студенту нужно только вспомнить назначение машины.

---

## 7. Flow D — Рабочий цикл экскаватора

### Цель

Связать 3D-анимацию с учебным объяснением.

```text
Экскаватор
→ Рабочий цикл
→ Запустить
→ Наблюдать фазу
→ Пауза
→ Выбрать фазу
→ Посмотреть объяснение
→ Продолжить
```

Во время цикла интерфейс должен отображать:

- текущую фазу;
- прогресс;
- название движения;
- связанные элементы машины;
- продолжительность фазы или цикла, если она используется в модели.

---

## 8. Flow E — Цифровой эксперимент с производительностью

### Цель

Научить причинно-следственным связям.

```text
Экскаватор
→ Производительность
→ Исходный сценарий
→ Изменить параметр
→ Сделать прогноз
→ Пересчитать
→ Сравнить
→ Объяснить результат
```

Желательный порядок:

1. показать исходное значение;
2. предложить изменить один параметр;
3. попросить предположить направление изменения;
4. выполнить расчёт;
5. показать результат;
6. предложить краткое объяснение.

---

## 9. Flow F — Эксперимент с количеством автосамосвалов

### Цель

Показать баланс механизированного комплекса.

### Маршрут

```text
Производственная система
→ Исходный сценарий
→ Количество самосвалов = N
→ Запуск
→ Результаты
→ Изменить N
→ Повторный запуск
→ Сравнить
```

Пользователь должен видеть:

- число самосвалов;
- производительность комплекса;
- загрузку экскаватора;
- простой экскаватора;
- ожидание самосвалов;
- продолжительность работ;
- затраты.

---

### F1. Недостаток транспорта

Сценарий должен позволять увидеть ситуацию:

```text
транспорт не успевает возвращаться
→ экскаватор ждёт
→ падает производительность комплекса
```

---

### F2. Приближение к балансу

При увеличении количества транспорта:

```text
простой экскаватора снижается
→ производительность растёт
```

---

### F3. Избыточный транспорт

После достижения достаточного количества транспорта:

```text
добавление ещё одного самосвала
→ небольшой или нулевой прирост производительности
→ больше ожидания
→ выше затраты
```

---

## 10. Flow G — Сравнение двух вариантов

### Цель

Подготовить пользователя к инженерно-экономическому выбору.

```text
Сценарий A
→ Сохранить результат

Сценарий B
→ Сохранить результат

→ Сравнить
```

Сравнение должно включать:

| Показатель | Вариант A | Вариант B |
|---|---:|---:|
| Количество самосвалов | | |
| Производительность | | |
| Загрузка экскаватора | | |
| Простой экскаватора | | |
| Ожидание транспорта | | |
| Продолжительность | | |
| Эксплуатационные затраты | | |

После сравнения пользователь отвечает:

> Какой вариант вы бы выбрали и почему?

---

## 11. Flow H — Учебное задание

### Цель

Проверить понимание без превращения MVP в полноценную LMS.

```text
Получить задачу
→ Изучить исходные условия
→ Настроить параметры
→ Запустить расчёт
→ Проанализировать результат
→ При необходимости изменить решение
→ Зафиксировать вариант
→ Обосновать выбор
```

Пример задания:

> Необходимо выполнить заданный объём земляных работ.  
> Подберите количество автосамосвалов так, чтобы уменьшить простой экскаватора без неоправданного роста эксплуатационных затрат.

---

## 12. Flow I — Ошибка пользователя как учебный сценарий

Система не должна блокировать нерациональный вариант.

Если пользователь выбирает слишком мало или слишком много машин, это является частью обучения.

Пример:

```text
1 самосвал
→ высокий простой экскаватора
→ система показывает последствия
```

Не следует выводить сообщение:

> Неверный выбор.

Предпочтительно:

> Экскаватор простаивает 38% времени.  
> Что ограничивает производительность комплекса?

---

## 13. Flow J — Возврат и история контекста

Навигационная модель должна поддерживать смысловой возврат.

Пример:

```text
Процесс
→ Этап «Разработка»
→ Экскаватор
→ Рабочий цикл
→ Назад
```

Ожидаемый результат:

```text
Экскаватор
```

Следующий возврат:

```text
Процесс
→ Этап «Разработка»
```

История должна отражать реальный маршрут пользователя, а не только URL-иерархию.

---

## 14. Flow K — Прямой вход по ссылке

Пользователь может открыть прямую ссылку, например:

```text
/machines/excavator
```

или:

```text
/processes/excavation-haul
```

В таком случае:

- страница должна быть работоспособной без предыдущего контекста;
- кнопка «Назад» не должна вести в несуществующий контекст;
- вместо этого используется стандартная иерархическая навигация.

---

## 15. Flow L — Первый запуск

Для MVP не требуется сложный onboarding.

Первый экран должен быстро объяснять три способа начать:

```text
Изучить машину
Изучить процесс
Решить производственную задачу
```

В первом техническом vertical slice доступны входы «Изучить машину» и «Изучить процесс». Третий вход появляется во втором vertical slice и ведёт в эксперимент с экскаватором и автосамосвалами; он остаётся частью полного MVP.

---

## 16. Обязательные состояния интерфейса

Для основных flows должны быть предусмотрены состояния:

### Loading

Используется при:

- загрузке 3D-модели;
- загрузке контента;
- инициализации сцены.

### Empty

Например, если для сущности ещё нет связанного процесса.

### Error

Ошибка загрузки 3D не должна делать весь учебный модуль недоступным.

Текстовая часть и расчётная модель должны оставаться работоспособными, если это технически возможно.

### Unsupported

Если функция ещё не реализована, интерфейс не должен имитировать её работу.

---

## 17. Навигационные сущности

Основные сущности, которые должны быть адресуемыми:

```text
Machine
Process
ProcessStage
ProductionSystem
Scenario
```

Желательно, чтобы каждая имела устойчивый идентификатор.

Пример:

```text
machine: excavator
machine: dump-truck

process: excavation-haul

stageId: excavation-stage
stageId: loading-stage
stageId: haul-stage
stageId: unloading-stage
```

Канонические идентификаторы определены в `docs/domain/domain-model.md`. Например, `Operation.id: excavation` и `ProcessStage.id: excavation-stage` обозначают разные сущности.

## 18. Минимальный набор экранов MVP

Для реализации полного пользовательского пути потребуются как минимум:

1. главная;
2. каталог машин;
3. учебный модуль экскаватора;
4. краткая карточка машины;
5. каталог процессов;
6. страница процесса;
7. экран производственной системы;
8. экран эксперимента/сравнения.

Фактическое количество URL и компонентов может отличаться.

Документ определяет пользовательские контексты, а не техническую маршрутизацию.

## 19. Acceptance flows по вертикальным срезам

### Первый технический vertical slice

Состав первого технического среза определяется в `docs/design/ui-ux-spec.md` §54: главная, каталог машин, модуль экскаватора, интерактивное 3D, выбор `bucket`, карточка компонента, рабочий цикл Play/Pause, связь «Где применяется», переход в процесс, страница процесса, выбор `excavation-stage`, compact card экскаватора, переход в полный модуль и контекстный возврат.

Первый технический vertical slice считается успешно собранным, если работают Acceptance Flows 1–4 ниже. Fleet simulation не входит в этот срез.

### Acceptance Flow 1

```text
Главная
→ Машины
→ Экскаватор
→ 3D-модель
→ Выбрать ковш
→ Увидеть описание
```

### Acceptance Flow 2

```text
Экскаватор
→ Рабочий цикл
→ Запустить
→ Пауза
→ Продолжить
```

### Acceptance Flow 3

```text
Экскаватор
→ Где применяется
→ Разработка и транспортирование грунта
```

### Acceptance Flow 4

```text
Процесс
→ Этап «Разработка»
→ Экскаватор
→ Краткая карточка
→ Полный модуль машины
→ Назад
→ Этап «Разработка»
```

### Второй vertical slice / acceptance полного MVP

Второй срез определяется в `docs/design/ui-ux-spec.md` §55 и включает fleet simulation, результаты и сравнение сценариев. Acceptance Flow 5 остаётся обязательным для полного MVP.

### Acceptance Flow 5 — Fleet simulation (второй срез)

```text
Производственная система
→ Изменить количество автосамосвалов
→ Получить пересчитанный результат
```

## 20. Что не должно происходить

Нежелательные пользовательские маршруты:

### Потеря контекста

```text
Процесс
→ Машина
→ Назад
→ Главная
```

### Дублирование сущностей

```text
Экскаватор в каталоге машин
!=
Экскаватор внутри процесса
```

### Скрытая магия

Пользователь изменил параметр, но не понимает, почему изменился результат.

### Декоративный 3D

3D существует, но не связан с учебной логикой.

### Мёртвые переходы

Кнопка показывает связанную сущность, которая не существует в предметной модели.

## 21. UX-принцип прогрессивного раскрытия

Пользователь не должен видеть всю сложность системы сразу.

Рекомендуемая глубина:

```text
обзор
→ контекст
→ детали
→ расчёт
→ эксперимент
→ решение
```

Пример:

```text
Экскаватор
→ что делает
→ как устроен
→ как работает
→ от чего зависит производительность
→ как работает с транспортом
→ какое решение принять
```

---

## 22. UX-принцип «объяснение рядом с действием»

Учебная информация должна появляться в момент, когда она нужна.

Примеры:

- выбрал ковш → увидел его назначение;
- изменил время цикла → увидел изменение производительности;
- добавил самосвал → увидел изменение простоев;
- выбрал этап процесса → увидел участвующие машины.

Не следует заставлять пользователя постоянно переходить в отдельный справочник.

---

## 23. UX-принцип обратимости

Исследовательские действия должны быть легко обратимы.

Пользователь должен иметь возможность:

- сбросить параметры;
- вернуться к исходному сценарию;
- отменить выделение;
- перезапустить цикл;
- сравнить с базовым состоянием.

---

## 24. UX-принцип явного базового сценария

Для экспериментов должен существовать базовый сценарий.

Например:

```text
Базовый сценарий
- 1 экскаватор;
- N автосамосвалов;
- заданное расстояние;
- заданный объём работ;
- заданные эксплуатационные параметры.
```

Пользователь должен понимать, что именно он изменил относительно базы.

---

## 25. Связь flows с learning goals

Пользовательские маршруты должны обеспечивать достижение learning goals.

Пример соответствия:

| User Flow | Learning Goals |
|---|---|
| A: машина → процесс | LG-M01–LG-M06, LG-P04 |
| B: процесс → машина | LG-P01–LG-P04 |
| D: рабочий цикл | LG-M03–LG-M05 |
| E: эксперимент с параметрами | LG-Q01–LG-Q04 |
| F: количество самосвалов | LG-S01–LG-S03 |
| G: сравнение вариантов | LG-S04, LG-E01–LG-E04 |
| H: учебное задание | интеграция всех уровней |

---

## 26. Критерий готовности пользовательской модели

Пользовательские flows можно считать определёнными для MVP, если:

- существует понятный путь от машины к процессу;
- существует понятный путь от процесса к машине;
- контекст сохраняется при переходах;
- одна предметная сущность переиспользуется в разных контекстах;
- 3D связано с учебными действиями;
- расчёт связан с изменяемыми параметрами;
- эксперимент приводит к интерпретируемым результатам;
- пользователь может сравнить варианты;
- пользователь может обосновать решение;
- ни один ключевой сценарий не требует знаний о внутренней архитектуре приложения.

Следующим source-of-truth после user flows должен стать:

`docs/domain/domain-model.md`

Он должен определить:
